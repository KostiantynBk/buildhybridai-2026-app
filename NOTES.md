# Scaffold notes

Open questions in paragraphs last processed by v1 are considered after the paragraph's next edit.

The unscored `eval/practice-v2/notes.json` is copied unchanged from the pre-implementation planning repository; it is invented practice data, not a held-out scored set. The code-only triage switch defaults to v2.1; Remote Config does not choose triage prompts. v2.1 makes no why-note call: it displays up to two current profile records selected by code. The legacy v2 negative-claim guard is a literal phrase check, not a general hallucination detector.

Angles receive only lineage/version pairs not previously considered on an adopted run; the full paragraph remains context. A candidate overlapping a live card from an earlier version of the same paragraph is held as a display-only repeat when its source angle or effective label matches; this never links identity or affects staleness.

The v3→v4 migration conservatively seeds considered pairs from existing cards and completed angles on the still-current paragraph version; unprovable history remains unmarked.

Revalidation in progress defers dependents without withdrawal; terminal failure or an unchecked outcome marks them uncertain, ends retained work and withdraws affected pending/approved questions as stale. A later edit requires new proof and does not restore withdrawn entries.

An edit between claim and dispatch may count an attempt that never reached the model; at worst a job gets one fewer retry. The 3-attempt bound is never exceeded.

Why-notes fingerprint every profile record supplied to the model, not just records it cites. A semantic edit or deletion hides the note and queues at most one persisted refresh; if that refresh races again, the note stays hidden. New records alone do not invalidate an existing note. Hashes remain local metadata, never question/Outbox content.

The `/dev` S1 rehearsal adds its invented private terms to Never send only after confirmation; use its Finish/Cancel cleanup button to remove terms added for that play. This does not restore replaced profile records or withdrawn Outbox entries.

## T04 local notebook, scheduler and profile

The original version-1 IndexedDB schema contains paragraphs, immutable paragraph-version records, items, profile, jobs, an empty Outbox store, and a migration marker. Version 2 adds lineage versions, dependencies and comparison batches; its upgrade gives each existing current item an independent initial lineage. `src/store/index.ts` is the only application IndexedDB boundary. The legacy localStorage notebook is read once, transactionally imported only into an empty notebook, and its key is removed only after commit. If key removal fails, a later retry sees the marker and does not duplicate the import. The migration marker is retained on delete-all so old content cannot be reimported. Clearing excludes Firebase's separate SDK storage and browser model downloads.

Paragraphs split on blank lines and trim boundary whitespace. Exact texts match first in old and new order. Remaining candidates use the Dice coefficient of distinct case-folded alphanumeric word-token sets, threshold 0.55; choose descending score, then shortest positional distance, then old index and new index. Each old/new paragraph participates at most once. Matching edits increment version and reset settle time; moves and boundary whitespace alone do not. On splits and merges only one eligible part retains an old identity. This deterministic lexical heuristic is not semantic identity and loses extra blank lines/boundary whitespace on reload.

The scheduler considers paragraphs at least 12 words after four seconds without a persisted text change, keys each extraction by paragraph ID/version/step, and checks the current version atomically at claim and result commit. UI edits pause scheduling until writes finish; an active comparison is not cancelled when the compared paragraph retains its identity, text and version. Current items from other versions are hidden; a successful new version supersedes older items. The store retains the items accepted by the evaluated extraction check, which matches quotes after case-folding and whitespace normalization; the returned quote is shown unchanged. Interrupted running attempts count as used: on reload they return to pending only below the three-attempt cap; an interruption at the cap is marked failed. Ordinary failures use five- and ten-second backoff. Privacy faults stop the job and pause the scheduler. There is no automatic re-preparation after model failure and no cloud fallback. Extracted paragraph text and a generic title go through the existing local service; profile content is not passed to any T04 prompt. Scored `/eval` remains separate.

The 6,000-character profile warning counts record text and free-form tags, without truncation or a new hard limit. A pending profile save does not clear newer draft edits.

The queue is one worker per tab, not a cross-tab lease: opening multiple tabs is not coordinated. The app runs only while open. If IndexedDB is unavailable or writes fail, the UI reports unsaved data. The copied synthetic demo-profile JSON is byte-identical to the pre-period planning file; its none/some/strong depth terms map to new/some/deep on import. End-to-end browser persistence and real local-model extraction remain to be checked by the user.

## T05 lineage and comparison

The unchanged D-019 `src/eval/scoring.ts::overlaps` is the eligibility check for linking quotes. It exposes a boolean rather than an overlap amount, so `src/pipeline/overlap.ts` duplicates only the occurrence and shared-length calculation to rank eligible candidates, importing the same `normalizeQuote`. Deterministic seeded equivalence tests compare the ratio threshold against the frozen scorer. Highest overlap wins; ties use earliest lineage creation order and then candidate order. T04 records do not preserve extraction order for simultaneous items, so migrated timestamp ties use a deterministic lineage-ID fallback, not an invented original order.

`compare.v1` runs only when an old quote is absent after the evaluated case/whitespace normalization; otherwise code returns unchanged without a model call. When that comparison says unchanged and the original quote is absent, code carries the old item forward without a lexical successor link; a reworded extraction can appear as a second item. This conservative duplicate is preferred over falsely attaching a dependency to a different subject. Comparison jobs share the foreground local-only service, durable queue, version checks and attempt cap. A cancelled comparison is refunded only before guarded model dispatch; dispatched interruptions count toward the cap. Failure leaves the previous lineage unchecked, not changed. Lineage and dependency state stays local. Run 2 uses each frozen target span as both the earlier statement and the earlier quote; shortcut results are labelled `code`, not model calls. A zero changed-row denominator is reported as null, and partial runs carry no automatic verdict. The user manually checked T05's basic paths on the laptop; Run 2 is in progress and no Run 2 result is claimed here.

When a changed comparison gives a verified replacement quote but no eligible extracted successor, the previous item remains the lineage content, the lineage advances as `needsConfirmation`, and its dependents are stale for that reason. The panel says it may have changed and shows the verified wording unless the evidence conflicts with another lineage. On later paragraph versions, a head's verified replacement evidence, whenever present, is its sole authoritative baseline for presence, comparison and successor matching; otherwise the item's quote is the baseline. If evidence is still present, code shortcuts to unchanged; if absent, it is used as both comparison text and quote, and an unchanged result carries the old item without falling back to obsolete displayed wording. A baseline-overlapping extracted item can link and clear `needsConfirmation`. Dependents of the older version remain stale, now with reason `changed` rather than `needsConfirmation`.

Before matching, a changed quote is conflicting if it overlaps another lineage's authoritative baseline present in the paragraph, or if it overlaps another changed decision's verified quote. All contenders are flagged without choosing a winner. Code keeps each previous baseline/content, marks the changed lineage `conflictingEvidence` and `needsConfirmation`, and hides the proposed wording; matching runs once with conflicting evidence excluded. This deliberately conservative rule can flag a legitimate merged sentence that expresses both claims. It operates on new batches only. Records written before T05 rev 4 may carry conflicting evidence; clear local data using Profile → Delete all local data after updating. This permanently removes the app's locally stored notebook, profile, items, history and jobs.

## T06 selection and local privacy interpretation

README §4's no-repeat rule is applied conservatively to both the model's source angle and the emitted angle. A profile change cannot bypass a previous source-angle pairing by relabelling it `track-record`, and at most one `track-record` card may be selected per item version. Session counts and tie-breaks use the effective emitted label. The Navigator accepted this interpretation before Run 3. Skill depths map `new/some/deep` to `2/1/0`; the strongest matching skill is selected independently per topic, and the item receives its highest topic score.

For legacy v1/v2 `track-record` selections, the triggering lesson (most shared topics, then lowest ID) is reserved in slot 1 of the why-note; remaining slots follow shared-topic count, lesson before skill, then ID. v2.1 instead displays the triggering lesson and scoring skill, in that order, or a preference only if neither qualifies; briefs show no profile block.

The question filter checks currency, emails, URLs, the user's explicitly listed terms and synthetic private tokens; it is not a general private-detail detector. Profile-text names are not automatically detected and must be added to the local never-send list. The URL check can conservatively hold back library names with TLD-like suffixes such as `socket.io` or `ASP.NET`, and text missing a space after a full stop; these are false positives, not leaks. The list is included in local profile exports but must not appear in shareable exports, prompts or the Outbox.

## Readiness recovery

A user can retry preparation from an error or unavailable state. The click starts both the browser availability check and Firebase's preparation call without first awaiting either; the SDK itself checks availability before initiating a download (`node_modules/@firebase/ai/dist/esm/index.esm.js`, `downloadIfAvailable` near line 1072 and `initializeDeviceModel` near line 3310). This keeps the SDK invocation within the click handler, but actual Chrome transient-activation behavior remains untested. SDK/device failures during jobs trigger a fresh availability probe, invalidate ready and reject the job without retry. Parse, schema and privacy-source rejections do not trigger a probe. A foreground check loops immediately before dispatch; in-flight work is not cancelled.

The config placeholder list is compared with `.env.example` in a test. Only exact example values or blank/missing values are rejected; ordinary project names are allowed.

## Limitations and open questions

- No-config and placeholder routes deliberately permit only notebook/navigation and browser availability; Firebase is not initialized, Prepare is disabled and private work fails closed. In explicit development debug mode a site key is not needed. The public `CustomProvider` (`node_modules/@firebase/app-check/dist/app-check-public.d.ts`) fails closed if invoked; the installed App Check source (`dist/esm/index.esm.js`, token handling near 756 and provider initialization near 1394) routes debug exchanges separately and the custom provider does not initialize reCAPTCHA. The SDK's debug console warning still applies.
- The state `downloadable` also covers a browser model already reported `available`: readiness here means prepared and warmed through Firebase, not merely downloaded. The status bar separately shows the browser's exact availability.
- `npm audit --omit=dev` reported four high findings in the Firebase → Firestore/Firestore-compat → grpc dependency chain. Firestore is not imported by this app. Bundle exposure and exploitability were not assessed; do not blindly apply the suggested breaking downgrade.
- Real Firebase setup, App Check, Chrome downloads, warm-up and source verification have not been exercised in this ticket. The SDK debug provider may itself log a generated token and project identifiers; keep that console private.
- The notebook, profile, paragraph versions, items and jobs use browser IndexedDB; no multi-tab coordination, cloud research or deployment exists yet. No claim is made that the whole app is offline: browser model download and App Check may contact services.
- This is a FIFO within one page, not a cross-tab or durable queue. A queued job waits for a foreground page; in-flight work is not cancelled on hiding.
