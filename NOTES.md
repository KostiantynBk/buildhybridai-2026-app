# Scaffold notes

## Verified SDK facts

This project pins `firebase` 13.3.0, containing `@firebase/ai` 3.1.0. The installed `node_modules/@firebase/ai/dist/ai-public.d.ts` declares `getAI`, `GoogleAIBackend`, `getGenerativeModel`, `HybridParams`, `InferenceMode.ONLY_ON_DEVICE`, `OnDeviceParams.createOptions` / `.promptOptions`, `initializeDeviceModel(progress)` and optional `response.inferenceSource`. The on-device source string is `on_device`. `node_modules/@firebase/app-check/dist/app-check-public.d.ts` declares `initializeAppCheck` and `ReCaptchaEnterpriseProvider`.

The published [3.1.0 changelog](https://github.com/firebase/firebase-js-sdk/blob/firebase%4013.3.0/packages/ai/CHANGELOG.md) lists TTS speech metadata, a `getAI()` existing-instance options fix, and GoogleAI prompt-feedback mapping fix. It does **not** list an on-device or hybrid-specific change. The options fix is relevant to repeated AI initialization but does not establish a change in local inference.

Static inspection of `node_modules/@firebase/ai/dist/esm/index.esm.js`, `ChromeAdapterImpl.generateContent` / `createSession` around lines 1019 and 1162, shows a new Chrome session is created for each inference. `createSession` passes `onDeviceParams.createOptions` to `LanguageModel.create`, so its `initialPrompts` field is passed through if supplied. `generateContent` passes `onDeviceParams.promptOptions` to `session.prompt`, carrying `responseConstraint`. These are source observations, not a real inference test. The synthetic preparation warm-up does not set `initialPrompts`; the evaluation extraction prompts do.

`HybridParams.inCloudParams` is optional in `ai-public.d.ts`; the local-only path leaves it unset. The SDK internally defaults a cloud model name when omitted, so the application guard remains essential.

The same source's `chromeAdapterFactory` around 1224 and `callCloudOrDevice` around 2562 preserve the missing-adapter cloud-routing hazard: when `LanguageModel` is absent, the SDK can call cloud before considering `ONLY_ON_DEVICE`. This app checks the API before creating an adapter and immediately before every call, uses only `ONLY_ON_DEVICE`, then refuses to consume output whose actual source is not `on_device`. This guard cannot prove every browser/SDK behavior; a real on-device run and network inspection are still required.

## T03b Remote Config source inspection

The `firebase` 13.3.0 installed `node_modules/@firebase/remote-config/dist/remote-config-public.d.ts` declares `isSupported`, `getRemoteConfig`, `ensureInitialized`, `fetchAndActivate`, `getValue`, value source and fetch timing settings. The implementation in `dist/esm/index.esm.js` checks IndexedDB support, obtains an installation ID and token, and POSTs to `firebaseremoteconfig.googleapis.com/v1/projects/{project}/namespaces/firebase:fetch` (API key in the query). It sends SDK/app identifiers, installation ID and token, and browser language; ordinary network metadata such as IP also reaches Google. The app never sets custom signals. The SDK can include stored custom signals, so this feature uses its own named Firebase app/storage namespace and does not share settings storage with the AI service. It imports no Firebase Analytics and sets no user properties, personalization or experiments. The SDK has an optional Analytics experiment integration if Analytics is separately initialized; do not initialize Analytics or configure experiments for this feature.

The installed `@firebase/installations/dist/esm/index.esm.js` generates the installation ID with Web Crypto and stores it under an app-name/app-ID key. It can POST a registration to `firebaseinstallations.googleapis.com/v1/projects/{project}/installations` and can POST to the installation's `authTokens:generate` endpoint. Based on static source inspection, the Remote Config fetch and Installations request paths do not attach an App Check token; the installation token is a different credential. These observations are not a browser network capture. No Firebase console changes or real SDK fetch were performed.

The app fetches once in the normal notebook startup, asynchronously. Only the four non-private allow-listed keys are read. The SDK timeout is eight seconds; an outer ten-second deadline returns defaults, skips starting work after late support/storage checks and ignores late results. The SDK may continue an already-started request after the deadline. Evaluation imports built-in defaults directly, not the Remote Config boundary, and writes those defaults and sources into exports; its explicit extract prompt selector is recorded separately. T06 session playback must likewise use and record built-in settings. Future cloud tickets must apply the validated cloud switch, model and budget; none of those cloud calls exists yet. Remote settings cannot alter any local-mode or privacy guard.

Out-of-range budget values are rejected to the built-in cap and marked `remote-rejected`, following the ticket's explicit test cases; values are not silently clamped to the nearest endpoint. `prompt_set` selects only bundled, complete v1/v2 mappings. Real browser fetching, actual console parameter types, App Check interaction and network traffic remain unverified.

## T03 evaluation

The five v1 prompt systems, examples, input templates and schema texts are copied from the pre-submission planning draft and fingerprint-tested; profiles and practice notes are unchanged copies. Firebase AI 13.3.0's `LanguageModelCreateOptions.initialPrompts` and `LanguageModelMessage` are declared in `node_modules/@firebase/ai/dist/ai-public.d.ts`, and the browser source's `ChromeAdapterImpl.createSession` passes create options through. The `Job` path carries the system and example turns to the Firebase local-only model; the existing config/API and actual-source guards remain in force.

The approved `extract.v2` system and first example were written after the v1 Gate 1 result; they are fingerprint-tested. Its second example, input template, schema and code checks reuse v1. The local transport sends system, example A, then example B through `initialPrompts`. This SDK version supports that path; the app has no active instruction-prepending fallback or alternate inference route.

The SDK does not expose the native on-device session for context measurement; on-device `countTokens` throws. The harness reports character counts, not tokens. Prepare warm-up and the first evaluation call after reload are reported separately, not included in warm figures. The 200-word gate uses 20 calls and nearest-rank p95; failed gate calls have a greater-than-12-second scoring floor. The 5-size, five-repetition curve reports an unscored max of five, not p95. The fixed gate table remains in the runbook; the app reports counts/rates rather than an automatic verdict. The Navigator has ruled on boundary, zero-denominator, source and matching interpretation before any scored run. Measured runs require a user-reported on-device component name and version from Chrome's Broker State; the value is stored in page memory, recorded per run, and never sent to the model. It is not API verification of the model that answered. Results from different models require separate exports and a page reload. The user completed the extract.v1 Gate 1 evaluation on the reported Gemma 4 configuration; the result was STOP on restraint, and the v1 results remain part of the report. The v2 Gate 1 run was subsequently completed on the user-reported Gemma 4 configuration and passed; model identity is not verified by the API. `/eval` has not been clicked end-to-end with a fake model; it is covered by server-render and fake-run integration tests. The synthetic dataset has known human-label limitations.

## Readiness recovery

A user can retry preparation from an error or unavailable state. The click starts both the browser availability check and Firebase's preparation call without first awaiting either; the SDK itself checks availability before initiating a download (`node_modules/@firebase/ai/dist/esm/index.esm.js`, `downloadIfAvailable` near line 1072 and `initializeDeviceModel` near line 3310). This keeps the SDK invocation within the click handler, but actual Chrome transient-activation behavior remains untested. SDK/device failures during jobs trigger a fresh availability probe, invalidate ready and reject the job without retry. Parse, schema and privacy-source rejections do not trigger a probe. A foreground check loops immediately before dispatch; in-flight work is not cancelled.

The config placeholder list is compared with `.env.example` in a test. Only exact example values or blank/missing values are rejected; ordinary project names are allowed.

## Limitations and open questions

- No-config and placeholder routes deliberately permit only notebook/navigation and browser availability; Firebase is not initialized, Prepare is disabled and private work fails closed. In explicit development debug mode a site key is not needed. The public `CustomProvider` (`node_modules/@firebase/app-check/dist/app-check-public.d.ts`) fails closed if invoked; the installed App Check source (`dist/esm/index.esm.js`, token handling near 756 and provider initialization near 1394) routes debug exchanges separately and the custom provider does not initialize reCAPTCHA. The SDK's debug console warning still applies.
- The state `downloadable` also covers a browser model already reported `available`: readiness here means prepared and warmed through Firebase, not merely downloaded. The status bar separately shows the browser's exact availability.
- `npm audit --omit=dev` reported four high findings in the Firebase → Firestore/Firestore-compat → grpc dependency chain. Firestore is not imported by this app. Bundle exposure and exploitability were not assessed; do not blindly apply the suggested breaking downgrade.
- Real Firebase setup, App Check, Chrome downloads, warm-up and source verification have not been exercised in this ticket. The SDK debug provider may itself log a generated token and project identifiers; keep that console private.
- The notebook is browser `localStorage`, not durable IndexedDB; no multi-tab coordination, cloud research, profile storage, notebook-triggered extraction or deployment exists yet. No claim is made that the whole app is offline: browser model download and App Check may contact services.
- This is a FIFO within one page, not a cross-tab or durable queue. A queued job waits for a foreground page; in-flight work is not cancelled on hiding.
